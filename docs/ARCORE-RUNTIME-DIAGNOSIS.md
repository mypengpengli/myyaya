# 小米 12 Pro 深度异常排查

2026-11-05。设备 2201122C、Android 15 / 澎湃 OS 3，Google Play Services for AR 1.57.262640093。小丫176客户端SDK为1.48.0，177改为1.57.0与固定对焦。仅扫描台面，不驱动底座。

## 已取得的证据

用户确认镜头中心离台面约 10cm。在对应姿态建立会话参考面，随后完成约 20cm 的左右平移。参考面锚点保持 TRACKING，但平滑深度反复为十几米，原始深度缺测或有效点极少；不能将这轮记为测距或通行验收通过。

12:44～12:52 的应用进程原生日志包含：

- 334 行 `Only kUnrectifiedOriginal is supported for ComputeDisparity`，伴随 `kUnrectifiedPinhole vs. kUnrectifiedOriginal`。同一失败可能产生多行调用栈，次数不是独立失败帧数。
- 138 行 `FEATURE_DSP_CAM_IMU_DESYNC`，相机至 IMU 时间偏移约 14.62～27.39ms；日志所列阈值为 5ms。
- 该段没有 `FATAL EXCEPTION` 或 `VIO_RESET`；没有崩溃不代表测量准确。

Camera2 主摄特征报告 `timestampSource=REALTIME`，畸变系数为零。这只能作为设备输出记录，不能单凭零值认定驱动错误：ISP 也可能已校正图像。

这证明 ARCore 内部在报错，发生在网格分类之前。它不能单独证明所有异常均由设备配置导致，也不能排除应用相机配置影响。白桌面低纹理会影响深度覆盖，但不足以解释全部上述原生错误。

## 对照与处理顺序

1. 使用 Google 官方 `hello_ar_java` 示例，同一 SDK、手机、场景和 AR 服务做独立对照。仅增加每 500ms 的深度统计，不接入小丫融合、网格或电机代码。
2. 对比默认对焦和 AUTO，以及设备实际提供的 CPU 图像配置。Google [FocusMode 文档](https://developers.google.com/ar/reference/java/com/google/ar/core/Config.FocusMode)建议 AR 跟踪使用默认配置，拍照/录像时使用 AUTO。176显式使用AUTO，177改为已取得有效观测的FIXED；对照尚未证明单改对焦就能修好。
3. 如独立示例也复现，继续隔离客户端 SDK、AR 服务和设备配置；不通过缩放十几米结果或放松阈值伪造可通行区域。
4. 若原生深度确实不能稳定使用，再接独立的视觉深度来源，沿用现有时效、置信度与包络判断。仅通过已知高度计算射线与平面的交点，只能得到假设平面，不能证明瓶子或桌沿不存在。

本轮没有清除 Google AR 服务数据、卸载或降级服务，也没有修改手机系统标定。原始日志、Camera2 特征和个人环境回放均放在本地忽略目录，不进入仓库或 Release。

## 独立官方示例实测

已在同一手机安装独立 `hello_ar_java`，来源为官方v1.48.0 / commit `b73725b586bb18b622d6e1c6aee9650176d4679d`。增加原始/完整深度、置信度、时间戳和位姿统计；固定为水平面检测，允许通过启动参数更换对焦和CPU分辨率。没有使用小丫的投影、融合或网格代码。各会话重新启动进程，AR服务保持原版本。

每轮约35秒的静止对照：

| 客户端SDK | 对焦 / CPU图像 | 完整深度非零中位数范围 | rectifier错误行 |
| --- | --- | --- | --- |
| 1.48.0 | FIXED / 640×480 | 18.62～37.91m | 3 |
| 1.48.0 | AUTO / 640×480 | 25.86～46.96m | 0 |
| 1.48.0 | FIXED / 1280×720 | 无非零距离 | 0 |
| 1.48.0 | FIXED / 1920×1080 | 17.11～27.72m | 0 |
| 1.57.0 | FIXED / 640×480 | 无非零距离，置信度通过的raw也为0 | 0 |

这些静止测试不能替代有平移的精度测试。没有错误行不等于正常，不能根据这张表按错误次数选择分辨率。相同rectifier错误已在独立示例复现，但所有测距异常的根因尚未全部确认。

随后1.57.0 / FIXED / 640×480采集约96秒，用户在其中完成约20cm、15秒的左右平移。首次达到32个近处高置信度raw点后，后续110份完整深度统计的中位距离在0.455～0.930m，总体中位数0.676m；高置信度raw最多1653点，最后一份1633点、raw中位0.780m。整段105个不同raw时间戳，VIO重置及相机/IMU时差错误均0，但rectifier仍52行，其中45行在上述近处数据出现之后。

因此该配置能够在移动后取得近处深度，且原生错误并未彻底消失。没有严格同轨迹、同姿态A/B，不能把恢复全部归功于SDK升级或固定对焦；也没有独立逐点距离真值，不能宣称厘米级精度通过。

177采用这组实际取得有效数据的SDK/对焦配置，并增加启动门槛：至少3个不同的新鲜raw帧、跨度至少300ms，每帧至少32个0.2～4m高置信度点，才允许地图融合和新参考面标定。完整深度单独为十几米、空raw、重复帧和过期帧不能完成初始化。短暂缺深度保留已有参考面，已有观测依旧过期；跟踪丢失、暂停、新会话或时钟回退需重新准备。这个门槛仅表示存在持续近处观测，不证明测距准确或自动允许电机移动。

复现补丁保存在 [arcore-reference-diagnostics.patch](../scripts/arcore-reference-diagnostics.patch)，基于上述官方commit，保留原示例版权。应用补丁后用 `assembleDebug -PdiagSdk=1.57.0` 构建；启动Activity可传 `--es focus FIXED --ei cpuWidth 640`，更换AUTO/1280/1920各自重启进程。原始日志和画面继续只留本地。

## 参考报告的适用范围

Google ARCore 仓库 [issue 1793](https://github.com/google-ar/arcore-android-sdk/issues/1793)记录了其他机型在同一 AR 服务版本上的相同 rectifier 错误和相机/IMU 时间问题。型号、系统和症状并非完全相同，报告者的设备配置解释仍是排查线索，不是 Google 已确认的小米根因。

分析本地日志可运行：

```text
python scripts/analyze-arcore-log.py .tools/arcore-local.log
```

输出只包含计数、偏移范围和对照示例的深度统计；脚本不会联网或上传日志。
