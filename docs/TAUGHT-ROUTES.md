# 教路线与复走第一版

版本2.1.178起，2.1.179修订导航姿态。目标是在人工确认的真实平整地面上，固定手机/头部，从指定起点复走一条已教短路线；遇障停车，用户移开障碍后明确继续；到点后转身。不是任意起点、自由探索或自动绕障。

## 操作

1. 菜单 → 房间地图 → **教路线与复走**。这是应用内前台界面，复用现有蓝牙连接；普通地图/探针仍隔离电机。
2. 新建或打开地图，开始扫描。需要跨重启使用路线时，先登记并识别固定参照图。无参照图的路线仅在原定位会话内可复走。
3. 开始扫描并恢复定位，在“路线操作”中连接保存的底座。**先把脖子放到最低，确认后摄平视前方且能看到近处地面**，再点“固定最低导航姿态”→“保持当前位置”；默认不发送任何头部位置指令，不会把你手动放低的脖子重新回正抬起。可选“降到最低”复用社区`down / FED1 ff`，写入回执不代表实际高度已验证，仍需看实际画面。稳定至少600ms后才固定；填写该姿态下主镜头到底座中心的水平偏移，不能在行驶中抬低头。179之前的“回正”不适用于用户确认的最低导航姿态。
4. 选择**实际地面**并确认真实平整地面，填写底座尺寸。台面试验与录制回放不允许驱动。第一版留至少10cm观测余量。
5. 选开始教路线，人工带领同一安装姿态沿开阔短走廊移动，到终点完成保存。定位中断、明显跳变或手机倾斜变化会拒绝保存连续路线。紫线表示所选路线。
6. 在真实地面空旷处做一次200ms后退与120ms左转校验，控制器核对实际位移及转向；必要时自动校正左右映射。校验失败不开始复走。
7. 回到起点8cm内并恢复原朝向，选择开始复走。每次90～180ms短动作后，根据新位姿决定下一步。遇障、偏离路线、位置跳变、安装姿态改变、断连或后台时停车。
8. 障碍移开且观测恢复后，选择继续；位置偏离时需先放回暂停位置附近。红色停止导航按钮与本地中文“停止 / 停止导航”均可停止；界面会显示语音停止监听是否成功开启，未开启时使用按钮。

模型工具 `list_taught_routes` 查询真实已教路线，`open_taught_route` 打开指定路线与所属地图。第一版打开后仍需在手机确认定位和短动作校验再开始，工具返回不表示已经行驶或到达。它不会用普通动作循环拼凑“去客厅”。

## 与普通地面网格的区别

普通扫描页仍保留原始/平滑深度、分区覆盖、三帧和整车网格诊断。路线模式把用户确认的平整教学走廊作为先验，实时高置信度原始深度用于检查近处障碍/落差，不以“每一块地板此刻都有raw点”为运行前提。

新鲜深度不足会停止动作等待，不把异常距离当作无障碍；观测到障碍则进入暂停，需用户明确继续。它不使用语言模型、Hermes或网络连接做实时电机控制。LOOI已有悬崖/近边传感器保护、动作超时和停止仍由现有控制器执行。

社区SDK目前只确认固定动作码，尚无已验证的连续速度设定接口。缩短动作是分步控制，不等于已经标定出指定厘米/秒的连续低速。到点转身也不代表已经检测到用户的实际位置。

179同时检查估计相机高度（本次地图坐标）与俯仰/横滚：平整地面中高度变化超过2.5cm或倾斜变化超过约7°时，导航姿态失效、停止后续动作，需重新确认姿态和方向。高度是视觉估计，无法区分脖子滑动、车体上坡或定位漂移，不是脖子编码器反馈；因此本版仅限平整地面。最低姿态下若需用镜头高度标定，应重新量主镜头到地面的高度，不能直接沿用其他头部位置测得的10cm。

## 分层实现

- `TaughtRoute.kt`：安装偏移、路线教学、坐标绑定、校验编码、小步反馈控制；与Android/BLE无关，可模拟测试。
- `RoutePerception.kt`：人工确认走廊中的实时原始深度障碍检查，不改普通地形网格的语义。
- `TaughtRoutePanel.kt`：地面、固定姿态、短动作校验、操作与状态；路线保存在应用私有`taught-routes/*.yayaroute`。
- `RouteMotorGateway.kt`：带会话标识、顺序号、动作回执与停止的窄接口。
- `route-robot-session.ts`：复用社区BLE、独占运动控制、前台运行、本地停止监听；旧会话及普通头部/轮子动作不能抢占路线控制。
- `NavigationProbeScreen.kt`：共享AR界面。路线使用应用内Dialog保持真实前台；独立探针仍用Activity，回放始终没有电机接口。

路线绑定地图ID与参照图/坐标变换指纹；无固定参照时绑定原Session，重开后不会把旧坐标当当前位置。当前没有路线导出/导入界面；地图导出文件不包含独立路线文件。

## 完整相机与IMU录制

扫描页顶部可录制相机与IMU，仅保存在手机本地`navigation-probe/datasets`；单次最多90秒或约100MB，保留最近三份。它与之前只有深度/位姿的NDJSON不同。选择录制回放会打开独立无电机地图会话，不能用回放画面驱动真实底座。

使用ARCore官方Recording/Playback API。回放结果可能与当时或下一次回放不同，不能当作确定性物理真值；见[官方说明](https://developers.google.com/ar/develop/java/recording-and-playback/developer-guide)。

## 借鉴的成熟方案

用户要求对照扫地机器人，已核对以下原始资料：

| 方案 | 已确认的能力与限制 | 本项目采用的部分 |
| --- | --- | --- |
| [Nav2](https://docs.nav2.org/rolling/getting_started/navigation_concepts/environmental_representation/) | 2D代价地图区分未知、空闲、占据及膨胀代价，分层接收传感器数据 | 分离路线依据、实时障碍与路径控制；本版没有把整个ROS2/Nav2装进APK |
| [OpenBot](https://github.com/ob-f/OpenBot) | 手机承担感知和计算，专用车体固件负责低层控制；[固件](https://github.com/ob-f/OpenBot/tree/master/firmware)具备轮速光学计数及可选超声 | 手机与车体分层、闭环反馈和车体适配；LOOI目前未验证轮编码器接口，不假设具有相同里程输入 |
| [Valetudo](https://valetudo.cloud/pages/general/newcomer-guide/) | 替代云端控制，复用厂商固件，不是扫地机导航固件替代品 | 借鉴地图/任务界面分工，不能将它当成可直接替换LOOI导航的算法库 |

第一版使用Kotlin实现小规模路线控制，保留后续接独立里程来源、占据地图和规划器的接口。当前ARCore底层错误并未根治，地面实车往返、逐点障碍、停车距离及跨会话复走仍需分别验收；单元测试和桌面界面通过不等于这些实物测试通过。
