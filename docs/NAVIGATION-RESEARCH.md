# 识别人、声源引导、跟随与房间导航研究

初版日期：2026-10-27；导航补研：2026-10-30（Asia/Shanghai）。本文为一手官方文档、开源项目及仓库源码研究，**不代表导航已经完成实机验收**。
用户当前设备为已升级澎湃 OS 3 的小米 12 Pro，LOOI 已到货，基本移动与头部动作已有用户确认；视觉建图、跨会话定位和自主导航仍待开发验证。不将新增外设列为必买项，优先验证手机已有能力。
手机优先的具体选型、源码核查、当前手机 AR 服务检查及分步验收见 [无雷达房间建图与导航方案](PHONE-FIRST-NAVIGATION.md)。
本文补充 [APK 开发方案](APK-DEVELOPMENT-PLAN.md)，保留已有录像、语音、记忆和 Pi 路线；导航不作为首个基础 APK 的阻塞条件。

## 1. 能力要分别成立

| 用户目标 | 必需能力 | 不能替代它的能力 |
| --- | --- | --- |
| 识别人脸/人体 | 人脸或 person 检测、跨帧目标关联 | 看见脸框不等于知道此人姓名 |
| 认出主人 | 明确登记、身份特征与阈值、陌生人拒识 | 临时 tracking ID 不等于长期身份 |
| 朝声音方向靠近 | 声源方向、视觉确认目标、距离与可通行路径 | ASR、声纹与音量大小不直接提供完整位置 |
| 跟随主人 | 持续目标关联、相对位置、障碍观测和闭环运动 | 单次人脸识别或模型说“向前”不构成跟随 |
| 记住房间并去客厅 | 地图、重定位、房间区域/目标点、规划和控制 | 文本记忆“客厅在左边”不等于可导航地图 |

ML Kit 官方明确人脸检测与跟踪不识别个人；现有人脸模块可作为检测基础，身份能力另做登记与验证。[官方说明](https://developers.google.com/ml-kit/vision/face-detection)
人体检测可先评估含 person 类别的轻量模型；MediaPipe 提供 Android 实时相机检测示例，模型、速度与遮挡效果仍须实测。[Android 示例](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector/android)
背身、遮挡后重现和多人交叉需分别验收目标关联；首版允许用户手动选择主人，目标不确定时停止跟随并请求重新选择。

## 2. 分期原型与放行条件

| 阶段 | 最小交付 | 放行条件 |
| --- | --- | --- |
| N0 感知与运动台架 | 记录相机视野、身份候选、BLE 命令及传感原始帧；验证 STOP | 明确型号/固件；本地停止、命令时限和断连真实行为有记录 |
| N1 原地看向人 | 选定人脸/人体，按画面偏差做有限转向和俯仰 | 目标居中后停止；丢失/多人歧义不继续追；不要求自主前进 |
| N2 单房间跟随 | 目标关联、距离候选、短时运动和障碍停止 | 在指定地面与路线证明距离/目标有效；遮挡、接近过近、观测失效时停止 |
| N3 声源引导 | 先估计方向、转向搜索，再视觉确认人 | 静止/电机运行、自身播音、不同方位分别测；只有方向时不直接前进 |
| N4 记住房间 | 人工带走或遥控采集，保存地图与房间标签，仅显示当前位置 | 重启后重定位通过；能区分定位有效、丢失及新地图，不立即控制底座 |
| N5 房间目标点 | 固定起点到同房间目标，再扩展跨门口去客厅 | 定位、障碍地图、底盘标定与控制闭环通过；失败能停止并说明原因 |

N2 与 N3 可解耦：手机声源方向不可用时，仍能先完成视觉目标和跟随原型。
每期保存录像/轨迹、传感时间戳、控制命令和失败原因；验收记录应包含测试地面、光照、距离、路线与重复次数。
室内底盘能否越门槛、在地毯转向、通过窄门和持续载手机运行，必须用到货设备实测；视觉算法不能弥补机械通过性不足。

## 3. 手机视觉、VIO 与相机布局

Google 官方清单列出 **Xiaomi 12 Pro 支持 ARCore Depth API**，因此先做无新增外设的原型有依据；当前国行系统、AR 服务安装与运行能力仍须核验。[支持清单](https://developers.google.com/ar/devices)
ARCore 用相机和运动传感器进行运动跟踪；Depth 主要由运动估计，也可融合设备可用的硬件深度传感器，不能把 API 支持等同手机具有 ToF 硬件。
官方说明深度在约 0.5–5 米更准确，移动设备通常有助于结果；本机近距离、低纹理、暗光与动态人物效果另测。[Depth 原理与范围](https://developers.google.com/ar/develop/depth)

需要优先解决三个具体问题：

1. **前后摄朝向**：前摄适合屏幕面对用户时的社交；ARCore 前摄模式的相机跟踪为 PAUSED，平面和锚点等能力受限，不能直接复用为后摄式 VIO。[官方前摄行为](https://developers.google.com/ar/reference/java/com/google/ar/core/CameraConfig.FacingDirection)
   前后摄位置与底盘实际前进方向也须实测标定：屏幕面对用户时，后摄可能朝底盘后侧。后摄支持 ARCore 不代表行进前方障碍视野足够；同机无法同时覆盖主人目标与前向障碍时，先做分模式原型，不将后摄深度当作前方深度，也不据此立即购买硬件。
2. **并发与相机所有权**：先分“前摄社交”和“后摄定位”模式。后续需要同时工作时核验实际前后摄组合；ARCore 与 Camera2 也要按共享会话接入，不能各自抢开相机。[共享相机接口](https://developers.google.com/ar/develop/java/camera-sharing)
3. **俯仰外参**：VIO 输出的是相机位姿，导航需要底盘位姿。手机俯仰会改变相机到 base_link 的变换；最小原型固定安装与头部角度，再决定是否增加可靠角度反馈/标定。

先独立采集相机 pose、tracking 状态、深度/置信度和时间戳，测短路线闭环误差、停止后漂移、重启重定位及发热；不先把“有 pose”标为“可全屋导航”。
ARCore 本身不替代可持久化的机器人占据地图、房间语义和规划器。RTAB-Map 有 Android ARCore 适配，可参考其 pose/内参/深度读取作为独立建图 demo。[官方适配源码](https://github.com/introlab/rtabmap/blob/master/app/android/jni/CameraARCore.cpp)
地图保存后还要证明能重新进入同一坐标系；相机重启、地图版本变化或定位跳变时，不执行旧坐标的移动目标。

## 4. LOOI 已有传感基础与缺口

仓库 [fed9-sensors.ts](../mobile/src/device-tools/fed9-sensors.ts) 包含社区抓包与其设备校准所得的 dock、四个向下悬崖标志、前向 ToF 推测解码；这不是本项目设备的校准结果。
[looi-robot.ts](../mobile/src/device-tools/looi-robot.ts) 明确将前向 ToF 标为 provisional；传感器数据有接入基础，不能描述成“LOOI 完全没有测距”。
到货后逐项核验方向/极性、单位、有效距离、无目标值、通知频率和停止条件；保留无法解码的原始帧，不能把旧的“安全”标志当持续新观测。
目前未见已实现的轮编码器、轮速里程计或底座 IMU 位姿接口；现有 BLE 方向命令也不能直接视为精确的米/秒或弧度/秒控制。
单个前向距离与悬崖标志不构成全屋障碍地图；需验证手机视觉是否补足可通行区域和近场观测，再考虑是否需要额外传感器。
需测命令到实际运动的延迟、直行偏差、转向响应、滑移、制动距离及限时命令；同一控制层统一手动、跟随与导航，禁止多方同时写 BLE。
BLE 已断开后手机无法保证再发送 STOP；底座自身超时/断连机制必须实测，软件不宣称“断连必停”。

## 5. 声源方向 DOA 的可行边界

ASR 识别话语，声纹关联身份，DOA 估计声音方向；三个模块分别验收，不能由“识别出主人声音”推导方位或距离。
Android 可查询活动麦克风的通道映射、位置与方向，但位置可能未知，多个麦克风也可能经 HAL 合成为处理后通道。[MicrophoneInfo](https://developer.android.com/reference/android/media/MicrophoneInfo)
第一步只做手机音频能力探针：记录独立通道数量/映射、采样同步与预处理，放置不同角度的声音源测方向误差；不根据手机物理麦克风个数承诺 DOA。
ODAS 是开源声源定位/跟踪候选，配置需要多通道原始数据和麦克风几何；可先离线验证算法，不能假设直接套在单声道录音上。[项目](https://github.com/introlab/odas)、[配置要求](https://github.com/introlab/odas/wiki/configuration)
若手机不暴露有效同步通道，再评估 USB 阵列及 Android 适配；这是候选补充，不是立即采购条件。
有可信方向后仍先转向与视觉确认；房间反射、自身扬声器、电机噪声、多人同时说话和目标消失均要测，DOA 本身不替代可走路径。

## 6. 轻量部署与 ROS 2 研究边界

| 层 | 建议职责 | 先期部署 |
| --- | --- | --- |
| 手机原生模块 | Camera2/ARCore、IMU、轻量检测、音频、目标关联、运动仲裁和停止 | 在现有 Kotlin/React Native 桥旁新增；先独立 demo 测资源 |
| 手机应用 | 主人选择、身份登记、地图/房间管理、状态展示与本地工具 | 保留现有 SQLite 与 Pi 桥，原始帧无需逐帧上传云端 |
| Pi 服务 | 解析“跟着我/去客厅”、检索身份与房间语义、提交与查询任务 | 只提交有参数和状态的高层目标，不运行每帧闭环 |
| 可选局域网计算 | 建图优化、可视化、ROS 2/Nav2 验证 | 先复用电脑；证明需求后再评估手机内嵌或协处理器 |

Nav2 需要完整变换、里程计、感知、地图定位、footprint 和底盘控制接入；它不是安装后自动识别 LOOI 的导航应用。[官方接入清单](https://docs.nav2.org/jazzy/configuration_and_development/first_time_robot_setup_guide/)
轮编码器并非 Nav2 的强制前提，VIO 等也可提供 odometry；关键是可靠的 odom→base_link、map→odom 与同步观测，不能写成“没编码器所以绝对不能导航”。[官方里程计指南源码](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/configuration_and_development/first_time_robot_setup_guide/odom/setup_odom.md)
建议先离线/电脑验证定位与控制接口，再决定引入 ROS 2；首版 APK 不直接承担整套 ROS 移植、全部 C++ 建图和手机视觉并发集成。
跟随与导航任务独立于聊天回答寿命；用户取消、目标/定位丢失或资源被录像占用时要明确暂停/停止，恢复后先重新核对目标与定位，不重播旧动作。

## 7. 原型数据和接口约定

身份记录使用 personId，短期目标使用跟踪会话内的 trackId；两者关联要记录置信度和依据，不能把临时编号永久写成人物身份。
房间记录至少关联 mapId、地图版本、roomId、用户命名、区域或到达点；“去客厅”先解析到当前有效地图中的目标。
位置和障碍观测保存采集时间、坐标系、有效性与置信度；超过本机验证的时效或定位丢失时，停止输出基于旧观测的运动。
高层任务可表达 follow_person(personId) 与 navigate_to_room(roomId)，实际是否注册依赖本机能力验收；不让模型直接拼接持续轮控序列。
相机切换、录像开始和头部角度变化均产生模式事件；导航/跟随先停止或进入可验证的暂停状态，资源恢复不自动延续旧速度。
首次验收记录每条路线的成功次数、目标丢失/错误切换、定位漂移、停止延迟和机械受阻；具体阈值在独立原型得到基线后确定。

## 8. 当前可承诺的下一步

先交付本地人脸/人体观测与手动目标选择、有限看向目标、手机后摄 VIO/深度日志，以及 LOOI 原始状态/运动标定记录。
依据这些原型决定单房间跟随、DOA 与地图方案；通过单房间重定位和目标点后，再开放跨房间“去客厅”。
额外硬件、完整 ROS 2 部署和自主全屋通行均保持条件性研究，不能由本次文档核查标记为已支持。
