# 导航开发调整：先复用方案，再用实测决定修改

更新：2026-11-10。用户要求减少围绕单段录像反复改代码，优先研究现成方案、采集不同条件的数据并验证实际表现。本文件替代“先让地板光流全部通过，再开始其他试验”的开发顺序；不代表自主导航已经完成。

OpenBot Android 目标导航实际将 RGB 图像、目标距离和目标方向送入训练后的策略，输出左右轮控制；ARCore 跟踪丢失时停止。固件文档明确说明轮速传感器及可选超声波的回传。它的成功不等于我们的低机位、履带、BLE 和缺少已确认轮编码器反馈的条件已经解决。

本次下载了七份上述固定版本的官方源码/说明到忽略目录 `.tools/navigation-reference/OpenBot`，用于逐项对照，没有把第三方源码复制进运行时。

## 当前证据与尚未证实的原因

- 188 真机单次 450 毫秒后退：用户确认移动、停止且脖子不变。ARCore 车身中心位移约 6.37 厘米；A4 图像近似 PnP 镜头位移约 6.95 厘米。两者量测对象和误差不同，不作为尺量真值。
- 189 已安装，170 项原生测试通过，但动作录像在手机端仍未通过累计地板光流验收。电脑原型成功不能替代手机结果。
- 新提取的一对原始 CPU 灰度图相隔约 166.47 毫秒，图像与位姿时间差约 1.93 毫秒。340 对点，手机拟合内点 200，比例约 58.8%，低于原 65% 门槛。
- 对完全相同的图像、像素点在电脑重新运行 LK，得到的目标像素位置与手机一致；电脑对相同地板点拟合也未过门槛。因此尚没有证据把此轮失败归因于 Android 专属 LK 实现或单纯 Kotlin 拟合错误。
- 失跟画面可见模糊，但曝光、振动、帧间隔、非地板特征及平面模型误差各自的影响还没有分离验证。不能写成“已确定唯一原因”。

地板光流保留为诊断与交叉核对来源。它失效时不提供伪造的累计位置，也不继续占住所有开发与试验时间。局部实测试验不要求先保存完整房间地图；正式自主行驶仍必须满足其所依赖的局部观测和停止条件，未知区域不能直接当空地。

## 下一轮实测顺序

每轮先明确起始状态、动作、记录内容和结束条件；用已有采集、限时动作、三秒倒计时和停止能力，优先不改 APK。用户手动连接，断连或重装后重新确认头部最低水平；需要手动压低时明确请用户操作，不自动发送回中/抬头。

| 阶段 | 要回答的问题 | 操作和验收 |
| --- | --- | --- |
| 1. 静止基线 | 当前光照和低机位能否持续提供新画面、位姿及障碍观测？ | 记录约 10 秒，不驱动。检查时间戳、图像清晰度、跟踪状态和深度覆盖；失败先查感知，不发运动。 |
| 2. 空地单次直行 | 运动期间是哪项先失效，停稳后是否恢复？ | 重新确认后摄方向平整空地、USB 余量和最低姿态。提示后只发一次已有 450 毫秒标定后退，自动停止，继续记录约 5 秒。记录电机起止、画面、ARCore、深度和光流；不得把限时停止写成障碍触发停车。 |
| 3. 静止障碍对照 | 罐子和纸盒在不同距离、位置是否被持续看见？ | 底座不动，由用户摆放障碍，比较中央/侧边、远近和不同光照。优先确认障碍出现后局部结果如何变化，不要求用户反复手持平移手机。 |
| 4. 靠近与停车 | 新鲜观测能否在接近障碍时终止动作？ | 仅在阶段 3 有稳定结果、近处停车链路经核对后执行低速小范围验收。记录触发原因、停止时刻和剩余距离；失败不自动重复。当前尚未完成这项验收。 |
| 5. 转向后重观察 | 能否重新看到侧方空地，再分段绕开障碍？ | 先独立验证转向与转后观测，之后才组合绕行。遇到未知先停并观察，不假设罐子背面已经可通行。 |

上表的“一米空地”是便于安排下一轮的场地要求，不是让它一次走一米。现有 450 毫秒动作约数厘米，实际距离仍应记录，而不是靠时长保证。

## 避免继续陷入局部算法

1. 同一个假设先做条件对照：静止/行驶、亮/暗、罐子/纸盒。不能只反复运行同一段录像。
2. 一轮只改变一个条件。每次失败必须记下可核对的停止原因，并选择下一轮要区分的假设。
3. 修改算法前写出要改善的实际指标；修改后重放旧失败样本，同时用新场景验证。没有改善就回退或替换路线，不再只累加复杂度。
4. 到点导航和记忆房间继续依赖可用定位；局部避障可以先单独开发验收。两项分别汇报，不用“能发运动指令”代替自主导航完成。

本轮没有新增实体运动。手机回放已暂停，临时 USB 全局常亮设置已恢复；下一轮先等用户确认实际场地与连接状态。
