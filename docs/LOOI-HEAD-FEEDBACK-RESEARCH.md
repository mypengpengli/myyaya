# LOOI 头部控制与位置反馈核查

核查日期：2026-11-09。研究阶段未再发送头部或履带动作。后续 2.1.184 已加入以下观测与诊断实现并覆盖安装，139项原生测试和完整源码CI通过。用户解锁并连接后完成两次只读实测；仍不能据此声称已读到实际机械位置。

## 184 本机只读结果

用户确认已解锁并连接底座。`robot_head_status` 两次返回连接正常，FED1 实际属性为 read / writeWithResponse / writeWithoutResponse / notify；不支持 indicate。两次读值均为 `ff`，订阅后目前没有记录到 FED1 通知。只读没有触发任何头部/履带写入。

重力模块正常，accuracy=3，稳定向量分别约 `[8.87748, 0.46157, 4.14097]` 与 `[8.87469, 0.46103, 4.14702]`。说明本机可持续获得稳定的手机倾角观测，不代表知道脖子的实际机械位置。联调记录编号 `820636466c2541eab7f45f4abcc2bf45`、`9ac7f4398e7a47a4a7cd505f22e07a03`，本机文件在 `.tools/phone/command-<编号>.json`。

准备做单次抬头前，已要求用户确认底座静止、手松开和当前头部位置；尚未发送新动作。需将动作后手机倾角与 FED1 回读/通知对比，不能因为初始读到 FF 就认定处于最低。

## 184 实现

- 新增独立 `robot-observation` Android 模块，只读取手机重力传感器，后台停采、清除旧样本；无相机和电机调用。
- 控制页显示手机倾角稳定性，可记录本次参考倾角；参考不代表最低姿态，不持久冒充机械标定。控制页聚焦期间保持亮屏，退出后释放。
- 明确的抬头/低头/回正命令先收集稳定参考，再发原有参数，观察 1.8 秒；区分未观察到明显倾角变化、倾角变化后返回、倾角变化和观测不足。所有结果仍返回实际位置未知；只能观察手机变化，不能把整车倾斜或纯升降分离出来。
- BLE 头部诊断只使用现有连接：检查实际属性，支持时读取 FED1 或订阅通知，超时取消；保留有限写入/回读/通知记录。不会为读取而自动连接或尝试任意字节。
- `robot_head_status` 为智能体和联调提供只读入口。原始字节始终标注语义未确认，不作为编码器或到位反馈。
- 联调排队请求由原生接收端加时间，超过 15 秒拒绝执行；状态请求和停止指令仍可用。传感器准备期间收到停止也会阻止随后写头部命令。

## 本机证据

- `head_up` 返回指令结束，用户确认明显抬高且底座静止。
- 第一次 `head_down` 因锁屏、断连未执行，待处理队列已被只读状态请求替换。
- 第二次 `head_down`（联调编号 `3e4ff6075a3f4d1b8532a3ed9dd8bf4e`）返回指令结束，但用户确认“没动”。因此低头未通过验收，不能标记为最低位置。
- 本机 SDK 的映射为上 `00`、中 `87`、下 `FF`，使用 FED1 无响应写入。调用完成只代表写入调用返回，不是机械到位回执。
- `executeChineseRobotCommand` 的直接 head 分支没有额外回中操作，并会暂缓普通自主动作；这不能排除所有其他调用者或固件行为。
- 183 的 `phone_status` 仅有连接概览，不能提供 FED1 属性；184 新入口已取得上述真实属性和原始回读。

## 公开资料：可用线索与限制

1. [ulooi 硬件探测实录](https://github.com/novolei/ulooi/blob/main/docs/m0-5-prototype-findings.md)：FED1 被列为 read/write/writeWithoutResponse/notify；作者记录 `00` 抬头、`5A` 回中、`FF` 低头后自动回中。作者将原因列为手势解释或机械保持限制的猜测，中间值尚未实测。**这说明不能假定 FF 可持续保持最低，不证明本机无动作的原因，也不证明读回值是真实位置。**
2. [andrey-tut 协议记录](https://github.com/andrey-tut/LOOI-Robot/blob/main/docs/PROTOCOL.md)：同样采用 `00/5A/FF`，明确没有已确认的头部位置反馈；FED1 暂按命令通道处理。
3. [FED9 实测说明](https://github.com/andrey-tut/LOOI-Robot/blob/main/docs/FED9_TELEMETRY.md)：`02` 为未完全解码的 IMU 类数据，明确不适合当作头部角度反馈；`0E` 也不能当作精确角度或里程。
4. [独立 My LOOI SDK](https://github.com/razor79/my-looi/blob/main/packages/looi-sdk/src/index.ts)：仍是 `00/87/FF`，与本项目相同；setHead 只写入，没有实际头部位置读取实现。因此沿用成熟 App 的命令映射也不能替代本机物理验收。
5. [LOOInteract](https://github.com/CozmoCyke/LOOInteract)：作者观察到不同的 GATT 写入/ACK 通道，并明确部分头部帧只证明被识别，未证明机械效果。不可把它的 ACK 当成本机到位反馈。

## 接下来的实现与验收顺序

1. 先在手机现有连接上导出只读 GATT 属性；只有本机特征实际支持，才尝试读取或订阅 FED1。记录原始值，不擅自解释为编码器位置。读到最后命令值不等于机械到位。
2. 把“命令已发送”“观测到手机倾角变化”“已确认最低位置”分别记录；无回读时返回未知，不能用“指令执行结束”暗示到位。
3. 使用手机自身重力/旋转向量观测相对倾角，参考 [Android 官方传感器文档](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position)。底座静止、手机装稳且无人触碰时可辅助判断是否发生倾斜；整体底座倾斜与脖子倾斜不能仅靠这一传感器分开，纯升降也不能由倾角确认。
4. 需要重新发头部动作时，先告知用户起始状态、预期方向和明显幅度，得到现场状态后一次一条测试；同步记录倾角、FED1/FED9、全部头部写入及用户反馈。先验证现有上/中/下，再决定是否验证有限的中间值，不批量扫字节、不发送混合履带动作的 FE00 帧。
5. 若仍无法明确低头行为，可用官方 App 的同一动作作物理对照，并分析该操作的 BLE 抓包；不依靠猜测修改参数。导航继续保持用户确认的最低姿态，头部调整后重建高度参考。

自主导航仍未完成；此次资料不能解决原有 VIO 高度波动、动作标定与通行区域验收，也不能作为已经可以自主行驶的证据。
