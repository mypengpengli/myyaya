# LOOI 头部控制与位置反馈核查

## 最新实机结论：186一次速度向下已到水平最低

用户手动连接后，原生诊断向下速度`0028`只执行一次350毫秒，原生350毫秒截止请求`0000`并收到停止ACK。用户明确确认“已经是水平的最低的姿态了”；手机倾角变化约30.4°，约182秒后的稳定快照姿态仍保持。此后一次200毫秒履带后退，用户确认脖子未变。这验证了本机这一次向下方向、原生桥及停止，不证明所有姿态均可定时归零，也没有验证速度向上。

FED1在速度停止后回读`0000`，仍更像命令/状态原始值，不能当实际位置编码器。常用`head_down`和导航“降到最低”仍用原单字节角度模式，尚未产品化切换为速度归位。导航继续保持当前已确认姿态；不得把下方历史“尚未验证”或“最低待确认”当最新结论。

核查日期：2026-11-09。研究阶段未再发送头部或履带动作。后续 2.1.184 已加入以下观测与诊断实现并覆盖安装，139项原生测试和完整源码CI通过。用户解锁并连接后完成两次只读实测；仍不能据此声称已读到实际机械位置。

## 最低位置纠正与186短时速度诊断

185用户随后确认：**虽然看到了下降，但仍明显抬着，没有到最低。** 不得据此恢复导航参考面或把软件回读FF标为最低。

继续核对官方客户端TrackMotionOffer/BaseVisionTrackingAdapter的实际调用，angle_speed用于跟踪时的头部速度，停止调用传0。186引入独立原生head-pulse模块，只复用当前BlePlx连接并写FED1，诊断方向固定候选幅值±40，单轮100～500ms，默认准备350ms。方向与本机机械效果尚未验证。

截止和后台停止由Android原生Handler触发，不依赖JS定时器。停止时会取消仍挂起的起始BLE事务，随后写两字节零速度；若停止ACK失败或超时，不自动重试运动，锁存阻止下一轮，须显式恢复停止并确认。STOP/后台generation防止异步派发的旧请求迟发。该软件机制不能证明机械最低或限位传感器存在，断连也不能假装停止ACK成功。

186新原生7项测试覆盖截止/缺ACK/失败锁存/恢复/后台停止/重入及参数拒绝；139项原导航测试与完整源码CI42575974452通过，已保留设置覆盖安装并核对手机APK摘要。常用语音和角度命令未切换为速度模式。新模块依赖现有react-native-ble-plx3.5.1的原生接口，升级时需专门验证。安装后蓝牙断开，已请用户手动连接；尚未验证此手机上的原生BLE桥调用，也未发送该模式的实体指令。

## 185 实机结果：用户已看到明显下降

连接后读到电量原始 `46 00`（首字节70）、客户端所命名的信息2A27原始 `01 02 0C`、2A28原始 `00 00 03`，FED1起始 `00`。这些信息字节未验证格式，不直接命名为某个版本号。

先发送一次FF有响应写入，倾角变化约2.23°，用户仍看不出下降。用户要求执行更多后，先说明绝对目标不能累加，再发送“回中87→抬头00→低头FF”，每步停稳后继续，履带不动。用户明确确认：**看到了明显下降**。该次低头的手机倾角峰值约5.17°。

后续两次只读稳定快照相隔76.10秒，手机倾角只差约0.0438°，没有额外头部写入；FED1仍FF，无头部通知。记录见工作交接中的联调编号，私下汇总为`.tools/185-head-trial-summary.json`。

结论范围：本机FF可产生肉眼可见的低头动作，保持该测试页面时未出现软件额外回中；本次不能证明有响应写入是成功原因，也不能证明FF回读是机械位置。没有把三步对照加入日常低头流程。最低位置仍待用户确认，后续导航不能直接把此次“下降”当作“已最低”。

## 184 本机只读结果

用户确认已解锁并连接底座。`robot_head_status` 两次返回连接正常，FED1 实际属性为 read / writeWithResponse / writeWithoutResponse / notify；不支持 indicate。两次读值均为 `ff`，订阅后目前没有记录到 FED1 通知。只读没有触发任何头部/履带写入。

重力模块正常，accuracy=3，稳定向量分别约 `[8.87748, 0.46157, 4.14097]` 与 `[8.87469, 0.46103, 4.14702]`。说明本机可持续获得稳定的手机倾角观测，不代表知道脖子的实际机械位置。联调记录编号 `820636466c2541eab7f45f4abcc2bf45`、`9ac7f4398e7a47a4a7cd505f22e07a03`，本机文件在 `.tools/phone/command-<编号>.json`。

准备做单次抬头前，已要求用户确认底座静止、手松开和当前头部位置；尚未发送新动作。需将动作后手机倾角与 FED1 回读/通知对比，不能因为初始读到 FF 就认定处于最低。

## 184 单次抬头与官方客户端对照

用户确认头稍抬、底座静止，并说明一直没有碰脖子。已发送一次 head_up（`e9ea8d928cda4edf85e3b0f6fdba9b7c`），峰值相对手机倾角约1.8645°，末态约1.7160°；用户反馈变化太小，无法辨认，因此**不算本次抬头物理验收通过**。随后只读（`52f51cec1f4d438d9ee2bf2f073d3c10`）FED1从FF变成00，记录只有00写入请求/返回与读00，没有其他头部写入或通知。这支持回读可能跟随命令值，尚不能证明是实际位置。

在用户手机已安装的官方包 `com.TangibleFuture.looiRobot` 2.9.2 / versionCode54 上，用 Android SDK apkanalyzer 检查公开可读DEX，不启动官方App、不连接其蓝牙。APK907139087字节，SHA256 `bef5c630d12a53c85a4e9136e16b2571e6f473d4e6ac2ddc768c41a30ed593a3`。APK、反汇编和辅助脚本仅保存在忽略的 `.tools/`，不发布第三方代码。

独立记录协议事实：

- `TangibleBody.toAngle` 的单字节编码为截断整数 `(1 - angle) * 255`，写FED1；没有据此发现现有00/FF编码算错。
- `TangibleBody.clamp` 是独立的 `angle_speed` 分支，FED1两字节 `[0, int(-speed * 127) 转为字节]`。它与角度模式不同，本轮**未发送速度帧**，不能假设可以直接替换已验收的角度模式。
- `BluetoothChannel` 该写入路径设置value后使用 Android 旧写入接口，没有显式设writeType。**不能因此断言官方使用有响应写入。** [AOSP实现](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/BluetoothGattCharacteristic.java)在支持WRITE_NO_RESPONSE的特征上默认选无响应；本机支持该属性，官方默认可能与小丫一致。
- FED9解析包含悬崖、evade左右数值、TOF、触摸、手机放置、电量、充电与序列回调；在检查的该分支没有机械头部角度字段。该版本把02解析为evade而非社区假设的IMU，0E解析为TOF；不要把社区低置信度解释当作实测机械反馈。

185保留生产默认无响应和00/87/FF，只加入DUMP权限保护的ADB单条head_probe，限定up/down/center和response布尔值，用相同参数排除写入方式因素；不是声称修复已成立。新增只读电量FED8、信息2A27/2A28（按该客户端命名为firmware/hardware）原始回读与模式记录。139项原生测试及完整CI42570713849通过，已覆盖安装且手机摘要一致。安装释放了蓝牙，已请求用户手动连接；185尚无新的实体动作结果或电量/信息读数。不得以蓝牙ACK当成到位反馈。

## 184 实现

- 新增独立 `robot-observation` Android 模块，只读取手机重力传感器，后台停采、清除旧样本；无相机和电机调用。
- 控制页显示手机倾角稳定性，可记录本次参考倾角；参考不代表最低姿态，不持久冒充机械标定。控制页聚焦期间保持亮屏，退出后释放。
- 明确的抬头/低头/回正命令先收集稳定参考，再发原有参数，观察 1.8 秒；区分未观察到明显倾角变化、倾角变化后返回、倾角变化和观测不足。所有结果仍返回实际位置未知；只能观察手机变化，不能把整车倾斜或纯升降分离出来。
- BLE 头部诊断只使用现有连接：检查实际属性，支持时读取 FED1 或订阅通知，超时取消；保留有限写入/回读/通知记录。不会为读取而自动连接或尝试任意字节。
- `robot_head_status` 为智能体和联调提供只读入口。原始字节始终标注语义未确认，不作为编码器或到位反馈。
- 联调排队请求由原生接收端加时间，超过 15 秒拒绝执行；状态请求和停止指令仍可用。传感器准备期间收到停止也会阻止随后写头部命令。

## 本机证据

- `head_up` 返回指令结束，用户确认明显抬高且底座静止。
- 第一次 `head_down` 因锁屏、断连未执行，待处理队列已被只读状态请求替换。
- 第二次 `head_down`（联调编号 `3e4ff6075a3f4d1b8532a3ed9dd8bf4e`）返回指令结束，但用户确认“没动”。因此低头未通过验收，不能标记为最低位置。
- 本机 SDK 的映射为上 `00`、中 `87`、下 `FF`，使用 FED1 无响应写入。调用完成只代表写入调用返回，不是机械到位回执。
- `executeChineseRobotCommand` 的直接 head 分支没有额外回中操作，并会暂缓普通自主动作；这不能排除所有其他调用者或固件行为。
- 183 的 `phone_status` 仅有连接概览，不能提供 FED1 属性；184 新入口已取得上述真实属性和原始回读。

## 公开资料：可用线索与限制

1. [ulooi 硬件探测实录](https://github.com/novolei/ulooi/blob/main/docs/m0-5-prototype-findings.md)：FED1 被列为 read/write/writeWithoutResponse/notify；作者记录 `00` 抬头、`5A` 回中、`FF` 低头后自动回中。作者将原因列为手势解释或机械保持限制的猜测，中间值尚未实测。**这说明不能假定 FF 可持续保持最低，不证明本机无动作的原因，也不证明读回值是真实位置。**
2. [andrey-tut 协议记录](https://github.com/andrey-tut/LOOI-Robot/blob/main/docs/PROTOCOL.md)：同样采用 `00/5A/FF`，明确没有已确认的头部位置反馈；FED1 暂按命令通道处理。
3. [FED9 实测说明](https://github.com/andrey-tut/LOOI-Robot/blob/main/docs/FED9_TELEMETRY.md)：`02` 为未完全解码的 IMU 类数据，明确不适合当作头部角度反馈；`0E` 也不能当作精确角度或里程。
4. [独立 My LOOI SDK](https://github.com/razor79/my-looi/blob/main/packages/looi-sdk/src/index.ts)：仍是 `00/87/FF`，与本项目相同；setHead 只写入，没有实际头部位置读取实现。因此沿用成熟 App 的命令映射也不能替代本机物理验收。
5. [LOOInteract](https://github.com/CozmoCyke/LOOInteract)：作者观察到不同的 GATT 写入/ACK 通道，并明确部分头部帧只证明被识别，未证明机械效果。不可把它的 ACK 当成本机到位反馈。

## 接下来的实现与验收顺序

1. 先在手机现有连接上导出只读 GATT 属性；只有本机特征实际支持，才尝试读取或订阅 FED1。记录原始值，不擅自解释为编码器位置。读到最后命令值不等于机械到位。
2. 把“命令已发送”“观测到手机倾角变化”“已确认最低位置”分别记录；无回读时返回未知，不能用“指令执行结束”暗示到位。
3. 使用手机自身重力/旋转向量观测相对倾角，参考 [Android 官方传感器文档](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position)。底座静止、手机装稳且无人触碰时可辅助判断是否发生倾斜；整体底座倾斜与脖子倾斜不能仅靠这一传感器分开，纯升降也不能由倾角确认。
4. 需要重新发头部动作时，先告知用户起始状态、预期方向和明显幅度，得到现场状态后一次一条测试；同步记录倾角、FED1/FED9、全部头部写入及用户反馈。先验证现有上/中/下，再决定是否验证有限的中间值，不批量扫字节、不发送混合履带动作的 FE00 帧。
5. 若仍无法明确低头行为，可用官方 App 的同一动作作物理对照，并分析该操作的 BLE 抓包；不依靠猜测修改参数。导航继续保持用户确认的最低姿态，头部调整后重建高度参考。

自主导航仍未完成；此次资料不能解决原有 VIO 高度波动、动作标定与通行区域验收，也不能作为已经可以自主行驶的证据。
